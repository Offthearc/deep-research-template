# Agent 2 — AI Unified Process (AIUP) — unifiedprocess.ai

## What the site actually proposes

AIUP is a named methodology ("AI Unified Process") for spec-driven, AI-assisted development. Core tagline: "Specs at the center. AI handles the rest." It inverts the usual code-centric relationship: use-case specifications are the authoritative source; code is a generated/regeneratable artifact.

| Element | Content |
|---|---|
| **Phases (4, overlapping/agile, not waterfall gates)** | Inception (vision doc, requirements catalog, BPMN, stakeholder alignment, test-strategy planning) → Elaboration (entity models, system use-case diagrams + business validation, architecture doc, test-case dev) → Construction (detailed use-case specs, supplementary specs — UI mockups, OpenAPI — AI-generated code, unit/integration tests, developer review) → Transition (UAT, continuous delivery, stakeholder feedback, production optimization) |
| **Roles** | Requirements Engineer (owns/maintains use-case specs for system lifetime); Software Engineer (reviews AI output, reverse-engineers legacy code in brownfield, implementation review); Stakeholders (continuous validation each iteration) |
| **Core artifacts** | Vision doc, requirements catalog, entity model, BPMN diagrams, use-case diagrams (PlantUML) and use-case specs (UC-XXX-*.md), architecture doc, supplementary specs (UI mockups/OpenAPI), test suites, generated code |
| **Two workflows** | Greenfield (AI drafts use cases/entity model from requirements → RE revises/owns → AI generates code/tests → SE reviews traceability); Brownfield (SE reverse-engineers entity model/use-cases/specs from existing code → both roles jointly baseline the spec) |
| **Six principles** | Requirements-centric; AI-assisted; Iterative improvement ("no perfect spec upfront," short cycles); Test-protected (tests guard behavior during regeneration); Stakeholder-centric; Traceable ("every line of code traces back to a business requirement") |
| **Change model** | Everything — new feature, change, bug — is modeled as a modification to a use case. New feature = new use case or new actor/flow on an existing one; change = modified business rule/alt flow; bug = disagreement between spec and code. "The specification changes first, and everything downstream follows from it." |
| **Tooling** | Claude Code plugin marketplace: `aiup-core` (stack-agnostic: `/requirements`, `/entity-model`, `/use-case-spec`, `/use-case-diagram`, Context7 MCP) plus stack plugins (`aiup-vaadin-jooq`, `aiup-angular-jpa`, `aiup-blazor-dotnet`) with `/implement` and stack-specific test commands. An "AI Unified Process Navigator" IDE plugin (IntelliJ/VS Code) links `@UseCase`-annotated tests to `UC-XXX-*.md` files via gutter icons. |
| **HITL / approval points** | Not gated as formal sign-offs but woven in as continuous review: stakeholder alignment (Inception), RE revision/ownership of AI-drafted use cases and entity model, business validation of use-case diagrams (Elaboration), SE/developer review of generated code+traceability (Construction), UAT (Transition). The tutorial states explicitly: "Review the catalog before continuing — this is your last chance to course-correct cheaply" — i.e., informal, expected-but-not-enforced review, not a hard gate in the tool pipeline itself. |

The "Three Layers" concept (What / Harness / How), described on the author's own blog rather than the main site, is a useful framing found in one of the linked articles: **What** = problem-space artifacts (use cases, entity models, in domain language); **Harness** (the "middle layer," called out as AIUP's key differentiator) = written-down engineering guardrails — naming conventions, package structure, test strategy, allowed/disallowed libraries, service-layer conventions — the tacit knowledge normally living only "in the heads of two or three senior developers"; **How** = the generated implementation. This maps closely to a project-level "constitution/harness" layer feeding per-feature generation.

## Lineage vs. classic Rational Unified Process

Classic RUP (Kruchten/Jacobson/Booch/Rumbaugh at Rational, unifying Booch/Objectory/OMT) is described as "iterative, architecture-centric, use-case driven, and risk confronting," with the same four phase names — Inception/Elaboration/Construction/Transition — organized around nine disciplines and heavy documentation templates ([RUP overview](https://www.ebsco.com/research-starters/computer-science/rational-unified-process-rup), [GeeksforGeeks](https://www.geeksforgeeks.org/rup-and-its-phases/)).

AIUP reuses RUP's four phase names and iterative/use-case-driven/risk-oriented spirit, but its direct intellectual lineage is **not** classic heavyweight RUP — it is Ivar Jacobson's later, deliberately lightweight **Use-Case 2.0 (2011)** and its 2023 refresh **Use-Case 3.0** ("a scalable, agile practice family... lightweight, scalable, versatile... a family of practices... mix and match... adding practices later if more detail is needed," per [Ivar Jacobson International's Use-Case 3.0 guide](https://www.ivarjacobson.com/files/use-case_3.0_v1.0.pdf)). AIUP's own articles list includes "Use-Case 2.0: The Forgotten Practice" and "Use-Case 3.0: The Refreshed Guide," and explicitly positions the process as descending from that agile use-case tradition rather than RUP's document-heavy, tool-vendor-driven (Rational/IBM) formalism. So: **same phase skeleton and use-case-driven DNA as classic UP, but the requirements-engineering practice itself is the slim, incrementally-elaborated Jacobson Use-Case 2.0/3.0 style, with AI substituted for the human coder as the "how" layer.** It is best characterized as a faithful adaptation of the *lightweight* branch of the UP family, not a resurrection of the bureaucratic RUP that agile methods rebelled against — one of the site's own articles is literally titled "Waterfall Was Never the Problem," signaling self-conscious positioning against the RUP-as-heavyweight-waterfall caricature.

## Useful vs. bloat assessment (for an anti-bloat, feature-based, ~15k-token-per-agent, two-gate pipeline)

| AIUP element | Verdict | Why |
|---|---|---|
| Use-case spec as the single artifact requirements changes route through ("spec changes first, everything downstream follows") | **Useful, core** | Directly matches a spec-first, feature-based pipeline; gives one canonical place to diff/approve before implementation. |
| Treating feature/change/bug uniformly as use-case modification | **Useful** | Removes special-casing in the harness; one workflow, not three. |
| "Harness" middle layer (naming conventions, package structure, test strategy, allowed libraries) as a separate, written artifact | **Useful, arguably essential** | This is exactly the project-level "constitution" that should be authored once and referenced by every per-feature pass, keeping per-agent context small since it's loaded as a compact fixed reference rather than re-derived each time. |
| Test-protected regeneration principle (tests as behavior contract surviving AI rewrites) | **Useful** | Aligns with spec→spike→implement where tests gate merge. |
| Entity model + BPMN diagrams + separate architecture doc + UI mockups + OpenAPI as distinct upfront Elaboration artifacts, all before any code | **Bloat risk** | Reintroduces a document-heavy Elaboration phase; for a 15k-token-budget per-agent pipeline this is too much upfront ceremony per feature — better suited as an optional, project-level (not per-feature) artifact set produced rarely, not regenerated every pass. |
| Four named phases (Inception/Elaboration/Construction/Transition) as the top-level project structure | **Partially bloat** | Useful as a *mental map* for what a one-time project-bootstrap pass should cover (vision, entity model, arch conventions) but should not be reenacted per feature; a per-feature pipeline only needs a thin slice of Construction+Transition (spec → implement → test → review), not the full four-phase march. |
| Two dedicated human roles (Requirements Engineer, Software Engineer) as institutional roles | **Bloat for small/solo pipelines** | Reasonable for AIUP's enterprise governance framing but overkill where the harness assumes one operator; can collapse into the two approval gates the user already specifies (pre-implementation spec approval ≈ RE sign-off; pre-merge review ≈ SE sign-off) without needing named organizational roles. |
| Continuous/informal HITL woven through every phase (stakeholder review "at every iteration") rather than fixed gates | **Needs tightening, not adoption as-is** | AIUP is deliberately loose about *when* review happens ("this is your last chance to course-correct cheaply" is advisory, not enforced by the tool pipeline). A harness with exactly two hard gates (pre-implementation, pre-merge) is stricter and more anti-bloat than AIUP's own tooling, which currently has no enforced gate at all — this is a genuine gap in AIUP worth improving on, not copying. |
| Brownfield reverse-engineering workflow | **Out of current scope** but useful pattern to keep in back pocket for legacy-code onboarding later. |
| Enterprise governance/audit-traceability framing (compliance, "every line traces to a requirement") | **Bloat for the target use case** | Valuable for regulated enterprises; unnecessary ceremony for a lean per-feature harness unless traceability is wanted purely as a lightweight nice-to-have (e.g., a comment link + Navigator IDE plugin pattern is low-cost and worth keeping). |
| Claude Code slash-command tooling (`/requirements`, `/entity-model`, `/use-case-spec`, `/implement`, stack-specific test commands) | **Directly reusable pattern** | Confirms the command-per-artifact-step approach the target harness is already gravitating toward; it's evidence this decomposition works in practice with Claude Code today. |

## How use-case creation could slot into a feature-based pipeline

- **Project-level, one-time (or rarely-repeated) pass:** Run something like AIUP's Inception+Elaboration once per project (or per major epic) to produce: a vision doc, a requirements catalog, an entity model, and — critically — the "Harness" layer (conventions, test strategy, allowed libraries). This becomes the fixed, compact context every per-feature agent loads (keeping within the ~15k-token budget because it's a small reference doc, not regenerated).
- **Per-feature slice:** For each new feature/change/bug, generate or update *just the relevant use-case spec* (AIUP's `/use-case-spec` granularity — one UC-XXX-*.md per unit of behavior) rather than re-running the full four-phase march. This is exactly AIUP's own Construction-phase granularity and matches "one feature at a time."
- **Gate 1 (pre-implementation):** Place the human approval gate at the point AIUP calls out informally — after the use-case spec (and any entity-model delta) is drafted, before `/implement` runs. This corresponds to AIUP's "Requirements Engineer revises and owns" step and the tutorial's "last chance to course-correct cheaply," but should be made a hard, enforced stop rather than AIUP's advisory framing.
- **Spike stage:** AIUP has no explicit "spike" concept — its pipeline goes spec → implement directly. A spike (exploratory, throwaway) stage would be a genuine addition on top of AIUP, best inserted between use-case-spec approval and full implementation for ambiguous/risky features only, keeping AIUP's own "test-protected iteration" principle for stabilizing the result afterward.
- **Gate 2 (pre-merge):** Maps to AIUP's Software-Engineer implementation review + traceability check + test-suite pass (Construction phase's "developer review cycles"), which AIUP already treats as a review point, again informally — worth enforcing explicitly.
- **Change/bug intake:** Adopt AIUP's rule that every change request first edits the use-case spec (not the code), with the bug-vs-enhancement distinction from the "Bug or Enhancement?" article (bug = code disagrees with existing spec; enhancement = spec itself must change) as the intake triage logic before a feature pass even starts.

## Source quality notes

unifiedprocess.ai itself is the primary source and is live, coherent, and internally consistent across methodology/enterprise/tools/tutorial/articles pages — treated as authoritative for what AIUP *claims*. It is a vendor/promotional site (selling a plugin marketplace and consulting/enterprise offering), so claims about outcomes ("audit-ready by design," efficiency gains) are marketing framing, not independently verified — reported as the site's claims, not as validated facts. The site does not surface token-budget, per-agent context-size, or explicit gate-enforcement details — that gap is real, not a research miss. The RUP comparison used standard secondary references (EBSCO, GeeksforGeeks) which are consistent with each other and with well-known RUP literature. The Ivar Jacobson International PDF for Use-Case 3.0 is a primary, authoritative source directly confirming AIUP's stated lineage. The "Three Layers" (What/Harness/How) content came from the author's personal blog (martinelli.ch), which appears to be the same author/voice behind unifiedprocess.ai judging by identical terminology and an "AIUP" article category — treated as a semi-primary elaboration of the site's own ideas, not fully independent corroboration.
